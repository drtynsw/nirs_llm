# RAG и BM25

Спецификация для КТ2. Требования НИРС: собственный индекс BM25 (готовые индексы
запрещены), тестовый набор запросов с ≥ 3 релевантными документами на запрос,
метрики Recall@k и MRR, обоснование предобработки.

## Документ и корпус

- Документ — статья закона; статья длиннее 350 слов делится по абзацам на
  фрагменты ~250 слов (`tk_81_1`, `tk_81_2`).
- Корпус — `data/corpus.jsonl`, 513 документов: ТК РФ, ГК РФ (подряд и услуги),
  422-ФЗ (самозанятые).
- Поля документа: `doc_id`, `law`, `article`, `fragment`, `title`, `citation`, `text`.
- Индексируем название статьи вместе с текстом: в названии часто стоит ключевой
  термин («Испытание при приеме на работу»).

## Предобработка (одинаковая для документов и запросов)

| Шаг | Решение | Почему |
| --- | --- | --- |
| Регистр | всё в нижний | «Работодатель» в начале предложения и в середине — одно слово |
| Ё → е | да | в законах «её», в вопросах пользователей обычно «ее» |
| Токенизация | регулярное выражение `[а-яёa-z0-9]+(?:\.[0-9]+)?` | слова и номера статей с точкой («312.1»); пунктуация и нумерация пунктов «1)» отбрасываются |
| Стоп-слова | служебные слова (предлоги, союзы, частицы) + слова-шаблоны вопросов: «можно», «ли», «как», «что», «какой», «мне» | вопросы пользователей начинаются с «можно ли», «как»; в законе таких слов почти нет, они только шумят |
| Лемматизация | `pymorphy3`, первая гипотеза разбора | русский сильно флективный: «уволить / увольнения / уволили» и «отпуск / отпуска / отпуском» должны совпадать. Библиотека лемматизации разрешена условиями НИРС |

Альтернатива лемматизации — стемминг (Snowball). Сравним оба варианта и вариант
без нормализации на benchmark и оставим лучший; результаты — в `benchmark/results/`.

Главная сложность корпуса — **разрыв словаря**: пользователь пишет «уволиться»,
«зарплата», «подработка», «не оформили», а закон — «расторжение трудового договора
по инициативе работника», «заработная плата», «работа по совместительству»,
«трудовой договор не заключен». Лемматизация этот разрыв не закрывает.
Как с ним работаем:

1. Мерим, насколько он велик: часть запросов benchmark пишем бытовыми словами.
2. Если Recall на них заметно ниже — добавляем небольшой словарь расширения
   запроса (`зарплата → заработная плата`, `уволиться → расторжение увольнение`),
   ~30 пар, составленных вручную по запросам *обучающей* части, и сравниваем
   метрики на *контрольной* части запросов.

## Индекс

Инвертированный индекс: `терм → {doc_id: TF}`. Дополнительно храним длину
каждого документа в термах `|d|`, среднюю длину `avgdl` и число документов `N`.
Структура (значения условные):

```
index = {
  "N": 513, "avgdl": 75.0,
  "doc_len": {"tk_70": 120, ...},
  "postings": {"испытание": {"tk_70": 6, "tk_71": 4, "tk_58": 1}, ...}
}
```

## Ранжирование

IDF и BM25 — в форме из методички НИРС:

```
IDF(t) = ln(1 + (N − DF(t) + 0.5) / (DF(t) + 0.5))

BM25(q, d) = Σ_{t∈q} IDF(t) · TF(t,d)·(k1 + 1) / (TF(t,d) + k1·(1 − b + b·|d|/avgdl))
```

Параметры по умолчанию: `k1 = 1.5`, `b = 0.75`. На КТ2 перебираем
`k1 ∈ {1.2, 1.5, 2.0}`, `b ∈ {0.5, 0.75, 1.0}` по benchmark.

Повтор терма в запросе считаем один раз (запросы короткие). Документы с нулевой
оценкой в выдачу не попадают. Если оценка лучшего документа ниже порога
(подбираем по benchmark и вопросам «не по теме»), считаем, что ответа нет (С4).

## Генерация ответа

- В модель передаём вопрос и top-5 статей с пометкой «[ст. N ТК РФ]».
- Инструкция: отвечать на русском, простым языком, 2–4 предложения; опираться
  только на переданные статьи и ссылаться на них; юридические термины пояснять;
  если ответа в статьях нет — так и сказать; не давать советов сверх текста закона.
- В конце ответа сервер добавляет оговорку «Это справка по тексту закона, а не
  юридическая консультация» (не доверяем модели её не забыть).
- Если поиск ничего не нашёл или оценка ниже порога — модель не вызываем (С4).
- Модель выбираем на КТ2 (кандидаты: YandexGPT, GigaChat, локальная через Ollama);
  ключ — в переменной окружения `LLM_API_KEY`.

## Проверка качества

Формат и черновик — `benchmark/README.md`.

- ≥ 30 запросов по темам, важным студенту: оформление, рабочее время, оплата,
  испытательный срок, отпуска и учёба, увольнение, ГПХ, самозанятость.
- Для каждого запроса ≥ 3 релевантных документа, размечают двое участников
  независимо, расхождения обсуждают.
- Запросы пишем как студент описал бы ситуацию, без копирования фраз из закона;
  примерно половина — бытовыми словами (проверка разрыва словаря).
- Метрики: Recall@5, Recall@10, MRR (формулы из методички НИРС), отдельно для
  «юридических» и «бытовых» формулировок.
- Сравнения: без нормализации / стемминг / лемматизация; разные `k1`, `b`;
  с расширением запроса и без.
- Результаты сохраняем в `benchmark/results/<дата>_<конфиг>.json`.
