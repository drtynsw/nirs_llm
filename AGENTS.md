# Правила репозитория

Файл читают и участники команды, и кодинговый агент. Работаем по схеме
Spec-Driven Development: сначала поведение и способ проверки, потом код.

## Перед изменением кода

1. Прочитай `spec/product/` и `spec/tech/`, относящиеся к задаче.
2. Если меняется поведение, API или формат данных — сначала обнови спецификацию.
3. Внеси изменение в код. Один логический шаг — один коммит.
4. Запусти `python -m unittest -v`. С КТ2 — ещё `python -m benchmark.run`.
5. Допиши запись в `CHANGE_HISTORY.md`.

## Ограничения

- Индекс BM25 пишем сами. `rank_bm25`, `Elasticsearch`, `Whoosh`, `sklearn`-поиск
  и другие готовые поисковые индексы запрещены условиями НИРС.
- Разрешены библиотеки лемматизации (выбор обоснован в `spec/tech/rag.md`).
- Приложение запускается командой `python -m app` без дополнительной настройки.
- Ключи API — только через переменные окружения или `.env` (он в `.gitignore`).
- Контракт `POST /api/ask` (`spec/tech/api.md`) не меняем без обновления спецификации и тестов.
- Корпус в `data/corpus.jsonl` не правим руками — только через `scripts/build_corpus.py`.

## Зоны ответственности

| Папки | Владелец |
| --- | --- |
| `app/retrieval/`, `benchmark/`, `scripts/`, `spec/tech/rag.md` | BM25 и RAG |
| `app/server.py`, `app/llm*.py`, `tests/`, `spec/tech/api.md`, `spec/tech/architecture.md` | Интеграция |
| `app/static/`, `spec/product/`, `README.md` | Продукт и интерфейс |

Изменения в чужой зоне — через pull request с ревью владельца.
